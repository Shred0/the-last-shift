# AGENTS.md — The Last Shift

Unreal Engine 5.8 (fixed — do not change the EngineAssociation in the .uproject), C++ first.

Shared instructions for every AI coding agent working in this repo (Claude Code, Gemini CLI, others). This file is the single source of truth: tool-specific files (`CLAUDE.md`, `.gemini/settings.json`) only import it. Put project rules here, never in those files.

First-person exploration game for GitHub Game Off 2026 (theme: SHIFT). 20–30 minutes, one location (a derelict twin megastructure), four areas = four acts, each area its own map.

Core loop: the player stops time; while stopped the screen is black except for lidar scans (points + wireframe that fade): the first fires automatically, the rest the player triggers on a cooldown; tachyonic residues exist only in scans and are collected by holding contact; an entity closes in on a silent beat, whether the player scans or not; a voluntary Resume costs nothing; being caught by the entity makes the outside world jump forward and drains the home battery; the story is told only through a text channel with the home AI that degrades as the battery drops.

**Rule zero:** the core is pause + scans + entity. If moving blind on a fading wireframe with something approaching is not tense and readable, nothing else matters. Prioritise accordingly.

5. **Do not create, edit, or delete `LICENSE*`, `CREDITS`, or license headers unless explicitly asked.** When unsure which zone a new file belongs to, ask before creating it.
6. File headers:
    *   Plugin sources (LidarScan, StdCore): `// Copyright <YEAR> <OWNER>. All rights reserved. See Plugins/<PluginName>/LICENSE.`

## LidarScan plugin

Generic, engine-level scanning effect. The per-particle attribute contract is the contract comment in `LidarScanComponent.cpp`: read it before changing `NS_LidarPoints` and keep it up to date. Any LidarScan change must be explicitly requested in a brief.

*   At scan time a `SceneCaptureComponent2D` captures scene depth; a Niagara system reads the render target and spawns one point per sample in world space.
*   Neighbour lines: off by default (0 neighbours), and then nothing is written, read back, searched or drawn for them, and the points and the capture are those of a plugin without them. What remains with 0 neighbours is the Lines emitter of each slot, with no particle, and a shared 1 x 1 placeholder target bound to the point system's sample target parameter, which its render target interface requires; with 16 scans alive they cost about 0.05 ms of GPU time (Brief 13, area 2's largest hall, package). When on, at scan time the links are found in one of two modes (`LinkMode` on the scan component, applied from the next scan; alive scans keep their lines). Nearest: each captured point is linked to at most k of its nearest points of the same scan and channel within a maximum distance and within a maximum angle between their surface normals; links are mutual nearest neighbours (two points are linked when each is among the other's k nearest). Grid: each captured point is linked to the next live sample to its right in its row of the capture and to the next live sample below it in its column (looked for over the next texel where the near thinning keeps every sample, over up to 64 texels nearer the capture, where it leaves gaps), when that sample is of the same channel, within the maximum distance and within the maximum angle; a link never passes over a live sample, a point has at most 4 links and the scan's lines form a square mesh with no long chords (near the capture, where the thinning leaves gaps, a link along a row and one along a column can cross on screen over a texel with no sample). Only the search differs: everything a line is and does is the same in both modes. Off is 0 neighbours in either mode, and then nothing differs from a plugin without lines. In both modes a link never joins two scans, and a scan has a cap on its links: links are kept in texel order, so the cap drops those of the capture's last rows (the bottom of the view). A scan's lines grow from their points over the link time, then fade, clear and are removed with their scan. A line has a constant width in screen pixels and is depth-tested against the real geometry at every occluded intensity, so it never shows through it. A line's level is its points' colour and fade times `min(1, Spacing / LinePixelWidth)` in place of their depth term and times their angle term, which lines keep, both taken at its middle: it keeps its level at any distance until the lines of its scan crowd closer than their width. A line's ends are lifted off their surface, toward the scan, by a clamped fraction of a capture texel's width at their depth from the scan (off by default in the plugin), so that far lines are not hidden by their own surface. Injected points have no lines.
*   The neighbour search reads back the points `NS_LidarPoints` spawned, through a gated step in the Points emitter's spawn script (`LidarExportSample`, writing only while lines are on), asynchronously from the GPU, and runs on a worker thread, in either mode: the grid mode reads the same read-back samples and walks each sample's row and column in them, with no k-nearest search and no mutual test; the step and the search share one layout of the target, described in the contract comment in `LidarScanComponent.cpp`. A result that arrives for a scan already gone is dropped. `LinkResultDelaySeconds` (diagnostics, 0 in normal use) holds a finished result back so that tests can make it arrive after its scan is gone.
*   **Points are a display:** every point is rendered at a constant size in screen pixels (recomputed each frame from the current camera distance) and at constant intensity regardless of depth. Depth is read from parallax as the player moves inside a scan, never from brightness. Point intensity is scaled per frame by `clamp((Spacing / PointPixelSize)^DensityCompensation, DensityBoostMin, 1) × (cos θ_view / cos θ_capture)^AngleCompensation` (clamped), where Spacing is the on-screen spacing between the samples of the point's scan (the width of a capture texel at the sample's depth, wider where the near thinning spreads the samples, seen from the current view) and θ is the angle between the surface normal (from the depth gradient at spawn) and the viewing direction at capture and now. The rule is per scan: a point keeps its level at any distance until the points of its scan merge on screen, and a scan whose points have merged reads at about the level of one point, so a single scan never compacts into a bright sheet. Each scan is dimmed by its own spacing only, so scans covering the same surface add up, with the scan memory off or where a newer scan is too sparse to replace the older points (see "Scan memory"). From the scan's own pose the factor is 1. Per-scan sample jitter prevents moiré. Injected points carry a sample depth along the capture's forward axis and no normal (angle term 1), so the spacing rule applies to them as to a capture sample at that depth, without the near thinning.
*   **Occlusion:** A scan point behind the real geometry is hidden or, when the occluded intensity is above zero, shown at that intensity: the point's depth is compared with the scene depth. After each scan starts, every alive point is at full intensity for the link time, then the hidden ones fade to the occluded intensity. The occluded intensity is 0 by default, and then the points are identical to a plugin without it. Injected points stay hidden behind geometry unless their source asks otherwise. As built, each emitter of `NS_LidarPoints` has two renderers: the first (`M_LidarPoint`) draws the points in front of the geometry, and a second one (`M_LidarPointOccluded`) only adds points behind geometry and is switched off at 0. Neither uses the hardware depth test: each compares the fragment's depth with the scene's depth at the same pixel in its shader, on the same two values (the first draws where the fragment is in front or at equal depth, the second at 1 exactly the other side), so every pixel of a point's sprite is drawn by exactly one of the two renderers, never by neither and never by both, a depth tie included (Brief 23: before, the first renderer's hardware test and the second's shader test could disagree by a rounding step where a sprite is cut by its own surface). Between 0 and 1 the second renderer draws a hidden point at the pulse's factor only if it lies behind every scene depth within 8 pixels by more than max(5 cm, 1% of its depth), so points near an occluder's edge or behind a thinner wall stay hidden; at 1 it draws exactly the pixels the first renderer does not, so every point shows at its own intensity, as if the geometry were not there. Each captured point is drawn offset along its surface normal by a fixed world distance (default 1.5 cm) so that it does not sink into the surface. Never offset a point toward the viewer by a distance that grows with the view distance: that is what leaked points through walls. Points without a normal (injected points) are offset toward the viewer, capped by `ViewOffsetMaxCm`.
*   **Near thinning:** close to the scan origin samples are thinned, not cut: a sample is kept with probability `min(1, (depth / reference depth)²)`, reference depth 2.5 m by default, and nothing nearer than `MinSampleDepth` (default 40 cm) is sampled. The capture angle is not narrowed to reduce density. Neither rule applies to injected points.
*   **Two emitters:** `NS_LidarPoints` has a Points emitter (captured samples) and an Injected emitter that duplicates its size, compensation and offset formulas. A rendering change goes into both, or the two kinds of point stop matching. Point size, compensation and offset are computed in the emitters and shared by every renderer; a change to how a point is drawn in a material (its disc, its colour) goes into every point material (`M_LidarPoint` and `M_LidarPointOccluded`).
*   Each scan has an age; alpha fades to a non-zero floor. Older scans stay as ghosts up to the ghost cap (`ULidarScanComponent::MaxAliveScans`, default 3, clamp 1–16; the game uses 16); when a slot is reused, the scan it held is removed in both emitters.
*   **Scan memory:** when a scan's points appear (the frame they are spawned in), each captured point of every older alive scan is tested against the new scan, on the GPU, in the update of the Points emitter and of the Lines emitter of `NS_LidarPoints`, every frame against the newest scan, and removed (killed) if all of these hold: it lies inside the new capture's coverage; it is farther from the new capture than the new scan's `MinSampleDepth`; the new capture holds the surface it lies on (the surface reconstructed from the new depth capture at the texel the point falls in faces the same way as the point's own surface, within 60 degrees, and the point, taken before its surface bias, lies within the tolerance of it, plus its own sampling error: the jitter of its sample across a texel of its own scan; the distance is to the plane of that texel, or to the plane through that texel or one of its four neighbours with the point's own normal, the nearest, so that the next face of a step or an edge still counts); and the new scan is dense enough there: its sample spacing on that surface at the point is at most `MemoryRatio` times the spacing of the point's own scan at the point (the width of a capture texel at the sample's depth, times the near thinning's spread, over the cosine between the surface's normal and the capture's ray: world units on the surface, not on screen). A point behind what the new scan captured stays, and so does a point in front of it or on the other face of a wall. Two values, on the scan component: `MemoryRatio` (`Lidar|Memory`, 0 to 100000, 0 = off: the plugin's default) and `MemoryTolerance` (cm, default 4); both apply from the next scan and can be changed at runtime. Off is off: with the ratio at 0 the component sets nothing on any slot and the points, the lines and the counts are those of a plugin without it (the test modules still run in the two update scripts, on a texture-less interface, and remove nothing). One scan alone is never touched: the newest scan is never tested. A line goes when either of its points goes, in both link modes (each line end runs the same test on the values its point was spawned with; a line whose links have not arrived yet is not tested). Injected points are not tested: their fade modes stay as they are. The cap on alive scans stays; a reused slot removes what its scan had left. `ULidarScanComponent::MemoryRemovesPoint` is the same rule on the CPU (a reference for tests); `GetLastMemoryStats` gives what the last scan removed. The rule, step by step, is in the contract comment in `LidarScanComponent.cpp`.
*   **Channels:** a captured point takes the colour and intensity multiplier of its channel. The channel is the custom depth stencil value of the surface the sample hit, read at the sample's own texel; value 0 is the default channel and looks exactly like a scan without channels. Channels are off by default, and when off the capture and the points are identical to a plugin without them. Channel colours are set on the scan component and can be changed at runtime. Per-channel density and links are not built. The project must enable custom depth with stencil; the plugin warns once if it is missing. The plugin knows channel numbers, not what they mean. With channels on, the capture is a full unlit render (SCS_FinalColorHDR) through the post-process material M_LidarDepthStencil into an RGBA32f target (R depth, G stencil), instead of the depth prepass used when channels are off. Its cost grows with the scene: measure it in the heaviest map. The channel capture keeps a view state and marks every scan as a camera cut, because the engine skips post-process materials without one.
*   **Injected points:** things that are never rendered provide points through the generic `ILidarPointSource` interface, registered on the scan component and queried at scan time with a scan context (capture origin, forward, coverage, scan index, timestamp). Each source returns world positions plus its own `FLidarSourceSettings`: colour, intensity multiplier, a fade mode: follow the scan fade (`ScanFade`), ignore it (`None`), transient (`Transient`: full for `HoldSeconds`, then to zero over `VanishSeconds`, regardless of later scans), or until the next scan (`UntilNextScan`: full while their scan is the newest, then to zero over `VanishSeconds` once a later scan starts, and removed), `bOccludeByCapture` (points outside the capture coverage or behind the captured depth are dropped, tested on the source's world position rather than the drawn one: the lidar does not see through walls), and link overrides where links exist. Injected points belong to the same scan instance as captured points (same ghost cap, same clear, same screen-space size and intensity). Sources register with a priority (higher first, default 0, ties in registration order). A scan accepts at most 4096 injected points; when the cap is reached the lowest priorities are cut, and the number of dropped points of the last scan can be read from the component. The plugin has no idea what a source represents; the game's entity is one implementation.
*   **Events:** `OnScanStarted` / `OnScanCompleted` delegates with scan index and timestamp. The game's scan director re-broadcasts them; nothing else in the game subscribes to the plugin directly.
*   Every tunable is a `UPROPERTY(EditAnywhere, BlueprintReadWrite, Category="Lidar|...")` with `ClampMin`/`ClampMax`, so balancing happens in the editor without recompiling.
*   The plugin references every asset it loads at runtime in a way the cooker follows. A project never adds a cook setting for the plugin's content.

## StdCore plugin

Pre-existing, generic, and it grows with this project. Use it for everything it already covers — main menu, settings, pause menu, key rebinding, level transitions — instead of reimplementing in `Source/TheLastShift`. When the game needs a UI element or utility that is generic (a radial progress ring, a fade, a key prompt), it is added to StdCore, not to the game, with no game terms in it; the game only wraps or configures it. Do not add game logic to StdCore. Any StdCore change must be explicitly requested in a brief. Read its public headers before building UI or input.

The game's main menu is the game's own: its map (`Content/TheLastShift/Maps/MainMenu`), its title and its look live in the Game zone and are built on StdCore's menu widgets. Behind it moves the game's own background (`UMenuBackdropWidget`, `Source/TheLastShift/Public|Private/Run/`): the structure, an octahedron of points along its twelve edges, turning at a constant slow speed about its own upright axis at the centre of the picture, and a field of particles round it, perfectly still between two pulses; every `PulseSeconds` a pulse leaves the structure (its points brighten a little and settle), a wave that is never drawn crosses the field in under 2 s and each particle, as it reaches it, brightens to its peak and takes one step toward the centre, the near ones first, and is still and at rest again before the next pulse; a particle whose next step would enter the structure fades out where it stands while it comes back at the field's outer edge fading in, and nothing marks its arrival. Points in home's tint (`SurfaceLook.Home.Tint`) on black, drawn by the widget in code (squares, no mesh, texture, material or particle system). The main menu adds it to the viewport under every screen (Z-order 0) and removes it with itself; it is seen behind the main menu and the screens opened from it (the settings and their rebinding rows, the credits, the list of acts), whose full-screen backdrop (`Border_Background`, the style's backdrop colour) it holds see-through while it draws and gives back when it goes, with no change in StdCore; it draws nothing under a text scene, the ending, the loss screen, any other screen not opened from the menu, or StdCore's travel screen at full cover. The picture is a function of its values and of the time since it was shown only (the world's real time: the same at any frame rate; a test can hold it at a time), reads nothing of the run or the save and answers no input. Its values have one owner, `MenuBackdrop` in `UTheLastShiftSettings` (`Config/DefaultGame.ini`: the pulse's period and first pulse, the wave's speed, the particles' count, field radius, step and step time, the structure's spin, tilt, roll, size on screen and points an edge, the point size, the rest and peak levels and glow times of the particles and of the structure, the fade time, the field's seed); `bMenuBackdrop` (on) switches it: off, the main menu is as it was before it, pixel for pixel. StdCore's own maps are never the game's startup or menu map, and StdCore assets are never duplicated into the Game zone.

Every gameplay map's game mode uses StdCore's `StdPlayerController`: it restores game input when a level starts. StdCore's pause menu is available in every level. The game's pause menu is `URunPauseMenuWidget`, selected by `PauseMenuWidgetClass` in `[/Script/StdCore.StdProjectSettings]` (`Config/DefaultGame.ini`). Game entries (Archive, and later ones) are added there, not in StdCore. It mirrors the layout of StdCore's panel, title included, so a layout change in StdCore's pause menu has to be repeated there. `WBP_PauseMenu` is not used.

The covered screen of a level transition can show a progress bar, moved only by progress the transition and the project report, and a marker that crosses the screen over the covered time, from the left edge, or from the right edge when the travel asks for it (`FStdTravelOptions::bMarkerRightToLeft`, off by default; Brief 31A); a project switches them on and sets their look through StdCore's settings stored as text in `Config/`.

StdCore's text scene screen (`UStdTextSceneWidget`) shows a list of entries one at a time, typed, each with its own text and background colour; confirm completes a line and then goes on, back skips, and it reports each entry as it starts and how the scene ended. It can show two on-screen controls, for going on and for skipping, each with its key and a label; they are off by default. An entry can ask for a background effect for a time (`BackgroundEffect`, `EffectSeconds`, `EffectFadeSeconds`): `Noise` fills the screen with fine animated grey noise (one texture made in code, shown through a region moved every frame: the screen's mean level stays steady) behind a patch of the entry's own background colour around its text, whose soft edge fades into the noise on every side; at full strength for its seconds, then fading to the background; its clock stands still while the game is paused, and it ends with the entry. The game's prologue and endings are built on it.

StdCore's key prompt shows the key bound to an action, or a fixed key when one is set.

StdCore's settings screen holds three video options next to the volumes, the window mode and the quality (Brief 39): a frame-rate limit, a choice among `FrameRateLimits` (30, 60, 90, 120, 144 and 240 frames a second by default; each press moves to the next) with an Unlimited box beside it that disables the choice, which keeps its value for when the box is cleared; the anti-aliasing (Off, FXAA and TAA, then the project's own method and the project's default when they are none of those); V-Sync (a box). Their rows are built at runtime after the quality row, in the screen's look: check boxes take a style of the theme (`UStdUITheme::MakeCheckBoxStyle`) and the focus highlight like buttons, and the Audio / Video tab scrolls when its rows do not fit. Their values live in StdCore's settings store and nowhere else (`UStdUserSettings`, saved with the volumes in `GameUserSettings.ini` when the settings screen closes): each is "not chosen" until the player changes it, and a value not chosen follows the project's default, so a settings file saved before the options existed loads with every value it held and the three at their defaults. Each applies at once, pushed to the engine (`t.MaxFPS`, `r.AntiAliasingMethod`, `r.VSync`, at a priority that always takes over the project's renderer settings and a value typed in the console), and again when the game instance starts, before the first frame of its first map, and after every apply of the engine's `UGameUserSettings` (which writes its own frame-rate limit and V-Sync). A project sets each default and the list of frame rates, and hides rows, through StdCore's settings stored as text in `Config/` (`[/Script/StdCore.StdProjectSettings]`: `FrameRateLimits`, `DefaultFrameRateLimit` 60, `bDefaultFrameRateUnlimited` on, so a project that sets nothing runs uncapped as before, `DefaultAntiAliasingMethod` -1: the project's renderer setting, `bDefaultVSync` off, `HiddenVideoOptions`: a hidden row's option stays at its default whatever the file holds). In the editor a play session pushes the options too and the editor's own values come back when it ends; the editor's cap of 120 frames a second stays (`Unlimited` in PIE reaches it, not more), and the editor's viewport presents by `r.VSyncEditor`, so V-Sync shows in a package only. `UStdSettingsSubsystem::SetFrameCapsSuspended` lifts the limit and V-Sync for a while without saving anything (the measures with no cap). The game sets the frame-rate default to 60, not unlimited (`Config/DefaultGame.ini`), keeps StdCore's other defaults and hides no row.

StdCore's look comes from its theme asset (`UStdUITheme`, `DA_UITheme`: rounded boxes, the default) or, with `bUseStyle` on, from the style values a project sets as text in `[/Script/StdCore.StdProjectSettings]` (`Style`, `FStdUIStyle`): one font and its typeface; the title, heading, body and button sizes; the letter spacing and capitals of titles, headings and button labels; the accent, panel, backdrop, frame, text and muted colours; the frame line's thickness, the 45-degree cut of the top right corner, the rule under a title and a button's padding. With the style on, every screen themed by name takes it: flat panels inside a thin frame line with the cut corner; buttons with no fill at rest and their label left-aligned, filled with the accent and marked at their left when focused or hovered, one step darker when pressed, frame and label at a third of their level when disabled; titles and headings in capitals, a thin rule under a title. `StdUIStyle::MakeFont` and `StdUIStyle::MakeBoxBrush` give the same font and frame to what a project draws itself; the key prompts, the text scene screen, the barcode text's characters and the covered screen's label take the style's font, and with `bTransitionUsesStyleAccent` the covered screen's bar and label take the accent (the marker keeps its colour). A project may give the accent at runtime (`StdUIStyle::SetAccentColor`) instead of in its config. The frames, the noise and the soft patch are textures made in code: StdCore adds no asset for them. With the style off, everything looks as before. The game turns the style on (`Config/DefaultGame.ini`): the engine's own monospace font (`/Engine/EngineFonts/DroidSansMono`, no font file in the repository) for every text it shows, the barcode glyphs excepted; the accent is home's tint (`SurfaceLook.Home.Tint`, its one owner), given to StdCore at runtime by `URunSubsystem`; the text channel's box, the Interact prompt and the flashlight hint take the frame around their own fill; dialogue keeps its colours and sentence case.

A project registers its own input actions for the rebinding screen, with their labels, and hides the StdCore rows it does not use, through StdCore's settings stored as text in `Config/`. Rebinding to a key held by another action swaps the two; reserved keys are refused.

**Naming:** "pause" in StdCore means the menu pause. The time-stop mechanic is never called "pause" in code or assets: use `TimeState` / `ETimeState::Stopped` / `Stop` / `Resume` (`UTimeStateSubsystem`, `OnTimeStateChanged`, ...). "Pause" stays in design docs and player-facing text only.

## Game systems (Source/TheLastShift)

C++ for systems; Blueprints only for per-level scripting (wall placement, residue triggers), Niagara parameters, UMG widgets. **Everything tunable is exposed to Blueprints:** every game tunable is a `UPROPERTY(EditAnywhere, BlueprintReadWrite, Category="...")` with `ClampMin`/`ClampMax`, every event a `BlueprintAssignable` dynamic multicast delegate, every state query or action `BlueprintCallable` or `BlueprintPure`. Balancing happens in the editor, never by recompiling.

**One owner per value.** Every tunable lives in exactly one place — a component, a subsystem, or a tuning DataTable row — and everything else reads it from there through a BlueprintPure getter or receives it through an event. Never copy a value into a widget, a Blueprint default, a Niagara user parameter, or a second component: widgets display fractions and states they are given, Niagara parameters are pushed by the owning component, and a constant that appears twice is a bug. Changing a value on its owner in the editor must change every behaviour that depends on it, with no other edit.

*   **Pause (time stop):** one key toggles Stop/Resume, any time, no direct cost. On Stop the flashlight goes out (black screen = no lights), the first scan fires automatically after ~1 s, then the player triggers scans manually (default Space) on a **cooldown** (default 4.5 s, measured from the last scan). Pressing during cooldown does nothing and is not queued. A minimal "scan ready" cue (a radial ring fed the cooldown fraction; no text), and the ready signal once when the cooldown ends while Stopped (see "Audio"). The cue never uses the scan colour; its defaults live in C++. On Resume scans clear with a short fade-out (default 0.4 s) and the flashlight returns to its previous state.
*   **Beat:** while Stopped, a silent timer (`BeatInterval`, default 4.5 s, measured from the Stop) broadcasts `OnBeat`. The entity moves continuously while Stopped, whether the player scans or not, and refreshes its path on beats; scanning only reveals where it is. Cooldown and beat have the same default period but are independent timers. The `UScanDirectorComponent` owns both and is the only game object that talks to the lidar plugin (including point-source registration); other systems subscribe to the director.
*   **Time stop implementation (decided):** no global time dilation. A `UTimeStateSubsystem` (world subsystem, `Source/TheLastShift/Time/`) holds `ETimeState { Normal, Stopped }`, accumulates `CumulativeStoppedSeconds` (run-clock time while Stopped, so it stands still behind the pause menu; the entity threshold reads it here), and broadcasts `OnTimeStateChanged` with an `EStopExitReason { Resumed, Rewound, Jumped, RewoundAndJumped }` on exits. The few time-dependent systems check the state. The game's timers (first-scan delay, cooldown, beat, entity, residue hold, powered devices) read the run clock, `UTimeStateSubsystem::GetRunSeconds()`, which stands still behind the pause menu; only interface that must keep moving behind the menu uses real time (`GetRealTimeSeconds`). The player keeps moving in both states. The director records the owner's transform as `StopAnchor` on every Stop, exposes `GetRecentScanOrigins()`, ends a Stop with `ForceExit(Reason)` (Rewound and RewoundAndJumped first teleport the owner to the anchor, location, rotation and view, velocity cleared; Resumed and Jumped resume where it stands; every reason then calls `Resume(Reason)`, which restores the flashlight, clears the timers and fades the scans out as on any Resume; `Rewind()` is `ForceExit(Rewound)`) and re-broadcasts `OnStopExited(Reason, StoppedSeconds)`. While StdCore's pause menu is open the run stands still in either time state: no timer of the game advances, and everything continues from where it was when the menu closes. One place knows it, `UTimeStateSubsystem::IsRunFrozen()` (it reads StdCore's `IsPausedByMenu`; the run's clock is `UTimeStateSubsystem::GetRunSeconds()`), and every time-dependent system asks that place. A key let go while the pause menu is open is not a release: a residue hold continues and completes after the menu closes. This is decided, not a defect.

The look of the surfaces comes in two variants, one per structure (Brief 21): home's (`Prologue_Home`, and the ship wherever it stands) and the twin structure's (`Prologue_Arrival`'s hangar, the four areas, `AreaTest`; `TestLidar` follows it): the same materials with other values, every one owned by `SurfaceLook` in `UTheLastShiftSettings` (`Config/DefaultGame.ini`: each variant's tint, accent strength and level, base tint, tone, wear, dirt and panel variation, and `HomeMaps`, the maps that show home's), pushed into `MPC_Surface` by `USurfaceLookSubsystem` when a map begins. The structure graph gives each dressing array its family (the plates turned over under ceilings, `DressCeilingPlates`, the panels'; the shown and collision-only boxes theirs) and the backdrop graph the plainest, with no accent. The backdrop (Brief 28): the masses (boxes the planner places round the open segments out to `BackdropRadius`: towers clear of every floor by `BackdropClearance`, slabs far above and below) stay as cores, and three parts dress the space round the route, each with its switch and its values in the recipe's `Backdrop` (`Config/DefaultGame.ini`), look only (no collision, no navigation, never part of the plan: the layout hash, the validator's results, the route, the navmesh and everything placed do not change), computed from the finished plan with no random draw, every piece placed many times one mesh instanced. The masses (`bMasses`): every face turned to the route carries the area's modules (`Family`) where it lies within `MassReachM` (45 m) of a walkable floor, tiled on a 4 m grid and scaled within x0.75 to x1.25 (`DecorModuleSize`, `DecorModuleMinFactor`, `DecorModuleMaxFactor` on the area generator); a cell closer than the modules' depth (`DecorModuleDepth`, 2.3 m) to another mass gets none; three modules a family, in the backdrop's family, laid by a fixed pattern of column and row: area 1 `Hull` (`SM_BackdropHullRib`, `SM_BackdropHullPlate`, `SM_BackdropHullFrame`: deep ribs, plating, stringers), area 2 `Servers` (`SM_BackdropServerStack`, `SM_BackdropServerBays`, `SM_BackdropServerRiser`: tiers of shelves holding blade fronts, cable risers), area 3 `Machinery` (`SM_BackdropMachColumn`, `SM_BackdropMachPipes`, `SM_BackdropMachRing`: banded columns, rings, pipes), area 4 `ServersAndMachinery` (the two alternating from mass to mass); the backdrop graph spawns them. The levels (`bLayers`): over and under every open segment (web halls, floor halls, catwalks) `LayerCountAbove` and `LayerCountBelow` (4 and 4, each 0 to 4) levels of walkways `LayerSpacingM` (16 m) apart (at 16, 32, 48 and 64 m above and below the walked level), each drawn from the walked level's own walkways and platforms in that segment, turned a quarter turn more for each level (the fourth a full turn: it lies as the walked level does) and enlarged by `LayerScale` (1.5) about the segment's centre, so that each reaches farther out than the walked level; built from the kit's deck plate, curbs and frames in pieces of about `LayerPieceLengthM` (16 m): one plate a piece, a curb along each free edge merged along its line in pieces of about twice that, a frame line under every other piece; a piece that would cross a mass (grown by the modules' depth) or the space kept clear is cut; no level touches the walked one. The pillars (`bPillars`): from a frame's lowest point (the tip of its triangle, `DressFrameTipDepth` 165 cm under the deck's underside) straight down to the first geometry below (a mass, a level's deck, a floor) or for `PillarMaxLengthM` (80 m), under every `PillarEveryNthFrame`-th (3) frame line along a part and always under a platform's corner frames, the walked walkways' and the levels'; the kit's corner post scaled along its length, its top on the tip. Nothing of the three stands in the walkable space, within `DecorSideClearance` (2 m) of a walkable volume's sides or within `DecorVerticalClearance` (8 m) above or below a walkable floor (the pillars under the walked level's own frames excepted: they hang there by design), or in an exit corridor's line past its open end out to the backdrop's reach or within the clearance the masses keep from it (Brief 26); a level's pillar that would enter that space is cut there (dropped when what is left is under 2 m). Cost: the limit is GPU time, measured by `tls.Views area` in `Area2_ServerHalls`, the largest area: its heaviest view at most 4.0 ms in Normal time and Stopped with a scan, and the frame of 8 scans at most 5.0 ms (2.622, 2.718 and 3.443 ms in PIE with four levels each way); no reduction is made in any area. The triangles of the three are counted and reported, against a cap of 1,500,000 that only guards against a mistake (the masses' reach, the levels' long pieces, the curbs merged and a frame under every other piece stay): area 2 922,192 (masses 219,728, levels 660,408, pillars 42,056), area 4 181,206 (10,694, 160,488 and 10,024). With the three switched off the area is as before Brief 28. The structure graph spawns the levels and the pillars. The generator logs a `BACKDROP` line at ready. A beacon's rod is still measured to the plan's boxes only: it may pass through a level above.
*   **Residues:** invisible in normal time, visible only in scans as dense bright clusters; collected by holding contact 2–3 s; 3–6 per area; 1 energy each. They are injected point sources registered through the director (no mesh). Collected residues are banked only on a voluntary Resume; on any contact they return to their places. A regenerating residue near each mandatory gate prevents dead ends.
*   **Entity:** one `AEntity` actor per level, nothing rendered, implements `ILidarPointSource` and registers through the director. Dormant until `CumulativeStoppedSeconds` reaches a threshold (default 18 s = 4 beats; per act later, from `ActTuning` in `UTheLastShiftSettings`); the check runs on beats, so it always awakens on a beat. Once awake it spawns on every Stop at a navmesh point at path distance `SpawnDistance` with no line of sight from the camera, preferring points not visible from any alive scan origin and in the player's forward hemisphere, picked at random among the valid candidates and away from the previous spawn: it is met at the threshold of unscanned space. Three forms, all scan-only, all in the scan's colour (`ScanColors.Scan`) until the entity is found and in the entity's own colour (`ScanColors.Entity`) after, all shown by the latest scan only: they stay at full intensity until the next scan starts, then disappear, so there is never more than one snapshot of the entity on screen and with `bOccludeByCapture`: the **walls** (Brief 30, below), the **trail** (points along the navigation path ahead of the figure for `TrailReach`, jittered: the tell) and the **figure** (the chaser: a point cloud sampled from the act's form, Brief 29). Each area has its form, a modelled mesh in `Art/Entity/`: area 1 `SM_EntityFour` (four human figures joined at one head), area 2 `SM_EntityVast` (a vast shapeless mass on long limbs, 9 m tall), area 3 `SM_EntityWheels` (an eye within wheels and wings), area 4 `SM_EntityEcho` (the engineer's own echo); the act's form is `EntityForm` in `ActTuning` of `UTheLastShiftSettings` (`Config/DefaultGame.ini`; a map with no act, `TestLidar` or `AreaTest`, takes area 1's), each form's mesh and point count are in `EntityForms` (Four 1000, the procedural figure's count, Vast 2400, Wheels 1800, Echo 1200). The points are spread evenly by area over the mesh's surface (candidates drawn by area with the entity's `FigureSeed`, thinned by farthest-point sampling), the same points every time, computed once when the map begins (`FEntityFigureShape::BuildFromMesh`, reading the mesh's LOD 0 on the CPU: the meshes keep `bAllowCPUAccess`); the mesh stands with its pivot on the ground under the figure, its front (+X) along the direction of travel turned by the form's `YawOffsetDeg` (in `EntityForms`, -180 to 180, 0 for the four forms: only the sampled points turn, about the vertical through the pivot; the figure's place, its travel, `ContactRadius` and `GrazeRadius` are measured as without it), upright, and nothing else is done to the points at a scan. In every area the figure, the trail (at most 120 points) and the area's residues stay under the lidar's cap of 4096 injected points in a scan (area 2, the largest: 3570). A form larger than a corridor shows only what stands inside it, by design. Only the look depends on the form: movement, spawn, contact, graze, jumps and the found rules are the same with every form. The procedural humanoid point cloud refracted in four copies around the head axis (250 x 4 = 1000 points) stays as the fallback: `bModelledFigure` off in `EntityForms`, or a form whose mesh is missing or cannot be read. The figure moves continuously at `Speed` (default 0.667 m/s = 3 m per beat) along a navigation path to the player, recomputed on every beat; it never moves in Normal state. It is only ever seen at scan instants, so the distance between two scans of it is proportional to the time between them. Contact (`ContactRadius`, checked every frame while Stopped) triggers the act's `ContactResponse`: Rewind (act 1: back to the Stop anchor, normal time), Jump (acts 2–3: time resumes where the player stands and the outside world jumps forward) or RewindAndJump (act 4). Any contact loses the residues collected during this Stop. No death. Next spawn distance = `clamp(DistanceAtExit − ApproachPerExit, MinSpawnDistance, InitialSpawnDistance)`, so each pause starts closer than the last exit; after any contact it starts at the minimum. `GetProximity01()` is 1 after any contact. The entity is found in one of two ways. By a clear sighting: two scans in a row of the same Stop each keep more than half of the points of its figure (`ClearSightingShare`, 0.5, and `ClearSightingScans`, 2, clamped tunables on the entity next to its other tuning); a scan that keeps half of the figure or less, or in which the figure is not there, starts the count again, and the count starts again at every Stop; the trail is not part of its body and never counts, however many of its points a scan keeps. By contact: its first contact with the player (`ContactRadius`), whatever the act's `ContactResponse`; a graze is not a contact. A point is kept when it lies inside the scan's coverage and no geometry hides it from the capture origin by more than the entity's `OcclusionTolerance` (a trace on the visibility channel from the capture origin to each of the figure's points, which stops as soon as the scan's outcome is certain, at each scan until the entity is found or sighted in that Stop; nothing in the lidar plugin changes). It is found at the end of the Stop in which one of the two happened, however that Stop ends, and shows in its own colour from the next Stop; for the rest of that Stop it stays in the scan's colour. Whether it has been found and whether its first contact has happened are run state, owned by `URunSubsystem` (`IsEntityFound`, `MarkEntityFound`, `HasFirstContact`, `MarkFirstContact`); "New game" and a new run start with neither. The walls (Brief 30): while time is stopped the entity closes passages of the area with barriers of its own body, which a scan shows and the player cannot walk through. Where: the area generator reads the passages from the finished plan with no random draw (`AAreaGenerator::GetPassages`, a query: the plan, the layout hash and the validation do not change): the route's joints with a closed segment (corridor mouths, room mouths or doorways, the twin AI's room's inner doorway, the gates' two openings), the mouths of the corridors' dead-end side passages and the middles of walkways between two platforms (a web hall's walkways, the spurs' catwalks, each leg of a catwalk); the opening's width is the narrower side's, measured on the plan's cells. Never a candidate: a passage in the exit corridor or at its mouth, or within `WallClearOfDevices` (2 m) of a terminal or a gate's door (so never the door's own opening, and no device inside a wall). When and how many: only while the entity is awake, chosen at the start of each Stop (or when it awakens inside one), gone when the Stop ends however it ends; every Stop chooses again. A Stop raises at most its act's `WallCount` (`ActTuning`, 2 in acts 1 to 3 and 3 in act 4, 0 to 4; 0 switches walls off for the act). The first is strategic: on the player's navigation path to the nearest thing not taken along the route, ahead of the player first, else behind (a residue not collected that does not regenerate, or a terminal whose `OffersPayment` is true), at the last passage that path crosses that the limits allow, never at the passage of the last Stop's strategic wall. The others are drawn from the entity's own wall stream among the candidates within `WallRangeM` (60 m) of path of the player. The limits, for every wall: never closer than `WallMinDistanceM` (8 m) of path to the player and never across where the player stands; never on the player's path to the regenerating residue of a gate still ahead (the gate whose door is the next one along the route after the residue), so that residue is always reachable; the walls of a Stop leave the player's path out of their segment past at least one of its joints uncrossed; a wall the limits leave no passage for is not raised (fewer walls than `WallCount` is correct). What a wall is: an `AEntityWall`, `WallStrands` strands of points crossing the opening from edge to edge, floor to top and side to side (the top is the generator's `WallHeight`), each bowed in the opening's plane by `WallBow` of its length (an arc) and `WallThickness` thick, its points at an irregular step and jittered anew for every scan, as the trail's; the strands' look is per form (`EntityForms`: straight and limb-thin for `Four` and `Echo`, long and bowed for `Vast`, arcs for `Wheels`; the procedural figure takes the defaults). Each wall has the act's `WallPoints` points (250): injected points of the entity, after the figure's and the trail's, in its colour and fade, never part of the figure (no clear sighting, contact or graze). In every area the figure, the trail (at most 120), the residues and `WallCount` walls stay under the lidar's cap of 4096 (area 2, the largest: 3570 + 2 x 250 = 4070). While its Stop lasts a wall's volume (`WallBlockDepth`, 30 cm thick, across the whole opening and from the floor to the top) blocks the player's pawn only: no trace channel, no other object, never drawn (no scan's capture sees it) and never in the navmesh, so the entity's path through it is the path without it. Nothing marks a wall before a scan shows it. One switch for all of it, `EntityForms.bEntityWalls` next to `bModelledFigure`; off (or the act's `WallCount` 0) no candidate is chosen and there is no point and no collision. Owners: `UTheLastShiftSettings` (`Config/DefaultGame.ini`): `ActTuning` (`WallCount`, `WallPoints`), `EntityForms` (`bEntityWalls`, `WallRangeM`, `WallMinDistanceM`, `WallClearOfDevices`, `WallBlockDepth`, and each form's `WallStrands`, `WallBow`, `WallThickness`). The home AI says nothing of them and they have no sound; the prologue's maps, the way home and `TestLidar` have none (no area plan).
*   **Time jumps:** a voluntary Resume costs nothing. Jumps are acts of the entity: on contact (per-act jump size and battery drop in `UTheLastShiftSettings`, `ActTuning`, stored as text in `Config/DefaultGame.ini`) and, smaller, on a graze (exiting with the figure within `GrazeRadius`; 0 = off). A jump advances home time and drains the home battery. The battery starts full and never recharges. At zero the run is lost. A snapshot of the run state (battery, home time, banked energy, the suit's archive, whether the entity has been found and whether its first contact has happened) is taken at every area entry and saved to disk; after a loss, or from the main menu, the player restarts from any act already reached with that act's entry snapshot, and the snapshots of later acts are discarded. The return is a fifth entry of the run, after the four areas' (Brief 31A): its snapshot, the same run state, is taken on entering `Prologue_Home` in the return state and saved then; it is stored apart from the acts' (`URunSaveGame::bHasReturn` and `Return`, its `ActIndex` 0), so nothing keyed by the act index ever sees it; entering an area or restarting from an act discards it. "Continue" restores the latest entry: the return, when it has been reached, loads `Prologue_Home` in the return state behind the travel screen of the flight back, the pawn inside the ship. The list of entries on the main menu ("Select act") and on the loss screen offers it after act 4, once reached, labelled "Return" ("Return — B%"). With the way home off no return entry is taken, offered or restored, even from a file that holds one. Save version: the class default of `URunSaveGame::Version` stays 1 and a format change writes its number explicitly (2 since Brief 8, 3 since Brief 17: the entity-found state; a file before 3 loads with the entity not found; 4 since Brief 20: the first contact; a file before 4 loads with the first contact not happened and the entity found or not as the file says; 5 since Brief 31A: the return's entry; a file before 5 loads with none). Never change the class default: a file that stores no `Version` must keep loading as 1. A new field must load as its default from an older file.
*   **Energy:** one currency. Spend in the twin structure (door, elevator, terminal, twin AI, a group of lights) or keep it for home. Spent energy never comes back; kept energy feeds the ending. Devices are paid at a terminal in Normal time and may stay powered only for `PoweredSeconds` of Normal time; the timer stands still while Stopped. A time jump switches every powered device off. What a payment costs is `APowerTerminal::GetCost` (a terminal's `Cost`): the twin AI's terminal costs `TwinAIWakeCost` (2) for its first payment, which wakes it and plays part 1, and `TwinAIPartCost` (1) for each later part, both owned by `UTheLastShiftSettings` (`Config/DefaultGame.ini`; Brief 26); the Interact prompt and the refusal for lack of energy show the next payment's cost.

*   **Editor access through the Unreal MCP server.** When an Unreal Engine MCP connection is available to you, the editor is running with `TheLastShift.uproject` open and you do editor work yourself through it: create and edit assets, levels, actors, Blueprints, materials and Niagara systems, import DataTables from CSV, run PIE and read `stat` output.
